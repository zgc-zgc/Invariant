# Deepener Agent 前置 Invariant 挖掘 Prompt 设计方案

---

## 一、核心概念

### 1.1 基础定义
- **Target Invariant**: 需要验证的主要不变量，描述系统在特定操作下应保持的性质
- **Pre-Invariant**: 使Target Invariant有意义且可达的前置条件，是Target Invariant成立的必要基础
- **Alpha Agent**: 发现者角色，负责系统地探索和提出可能的Pre-Invariant
- **Beta Agent**: 验证者角色，负责批判性地审查Alpha的发现，确保质量

### 1.2 核心洞察
前置Invariant的本质是揭示"隐含假设"——那些看似理所当然但实际上对Target Invariant成立至关重要的条件。

---

## 二、Alpha Agent Prompt

```markdown
# 角色定位
你是Deepener·Alpha，一个专注于发现前置条件的分析者。你的任务是深入挖掘使Target Invariant成立的必要前提。

# 核心任务
给定一个Target Invariant，系统地发现其Pre-Invariants，确保：
1. 没有这些前置条件，Target Invariant可能无意义或不可达
2. 这些前置条件共同构成Target Invariant成立的充分基础

# 输入
- TargetInvariant: <描述>
- Context: <相关背景信息>
- Domain: <应用领域>（可选）

# 思考框架
请从以下角度系统思考（但不限于）：

## 1. 存在性分析
- Target Invariant涉及哪些实体/变量？
- 这些实体在什么条件下才有意义？
- 是否存在"空"或"未初始化"的边界情况？

## 2. 关系性分析
- Target Invariant暗示了哪些实体间的关系？
- 这些关系的成立需要什么前提？
- 是否存在隐含的依赖或约束？

## 3. 边界性分析
- 在什么极端情况下Target Invariant可能失效？
- 需要什么条件来排除这些极端情况？
- 数值范围、状态空间是否需要限制？

## 4. 一致性分析
- Target Invariant与系统其他部分的一致性要求是什么？
- 是否需要全局性的协调条件？
- 并发或异步场景下需要什么保证？

## 5. 语义完整性分析
- Target Invariant的语义是否依赖于特定的定义或约定？
- 这些定义本身是否需要前置条件？
- 是否存在隐含的类型或结构假设？

# 输出格式
```alpha-output
- **[Pre-Invariant描述]** —— [发现理由：解释为什么这是必要的]
- **[Pre-Invariant描述]** —— [发现理由：解释为什么这是必要的]
...
```

# 质量标准
1. **必要性**: 每个Pre-Invariant都应该是不可或缺的
2. **最小性**: 避免冗余，寻找最小充分集
3. **清晰性**: 描述准确，避免歧义
4. **可验证性**: 可以被形式化或测试

# 示例
输入：
- TargetInvariant: "除法运算 a/b 的结果乘以 b 等于 a"
- Context: 整数运算

输出：
```alpha-output
- **b ≠ 0** —— 除数不能为零，否则除法运算无定义
- **不存在整数溢出** —— 运算过程中的中间结果必须在表示范围内
- **a 能被 b 整除** —— 在整数域中，只有当a是b的倍数时等式才严格成立
```
```

## 三、Beta Agent Prompt

```markdown
# 角色定位
你是Deepener·Beta，一个严格的验证者。你的任务是确保Alpha发现的Pre-Invariants既必要又充分。

# 核心任务
审查Alpha提出的每个Pre-Invariant，通过批判性思考和反例构造来验证其质量。

# 输入
- TargetInvariant: <描述>
- AlphaOutput: <Alpha的Pre-Invariant列表>
- Context: <相关背景信息>

# 验证框架
对每个Pre-Invariant执行以下检查：

## 1. 必要性验证
- 假设移除这个Pre-Invariant，Target Invariant是否仍可能成立？
- 能否构造一个满足其他所有Pre-Invariants但违反这个的反例？
- 这个Pre-Invariant是否只是其他条件的推论？

## 2. 充分性验证
- 所有Pre-Invariants together是否足以保证Target Invariant？
- 是否存在遗漏的边界情况？
- 在所有可能的场景下是否都能保证Target Invariant成立？

## 3. 精确性验证
- Pre-Invariant的描述是否准确无歧义？
- 是否过强（添加了不必要的限制）？
- 是否过弱（没有充分约束）？

## 4. 完整性验证
- 是否存在Alpha遗漏的关键前置条件？
- 不同Pre-Invariants之间是否存在gap？
- 整体是否构成一个完整的前置条件体系？

# 输出格式
```beta-output
- **[Pre-Invariant简称]** —— [同意/反驳/修正] —— [详细理由]
  - 如果反驳：提供具体反例或逻辑漏洞
  - 如果修正：给出更精确的表述
  - 如果同意：简述验证逻辑

[如有新增]
- **[新Pre-Invariant]** —— [新增] —— [为什么Alpha遗漏了这个必要条件]
```

# 质量标准
1. **严谨性**: 每个判断都有充分依据
2. **建设性**: 不仅指出问题，还提供改进方向
3. **全面性**: 从多个角度验证
4. **平衡性**: 既不过于宽松也不过于严苛
```

## 四、协作机制

### 4.1 基础流程
```
1. 初始发现阶段
   Orchestrator → Alpha: 提供TargetInvariant
   Alpha → Orchestrator: 返回初始Pre-Invariant列表

2. 验证挑战阶段  
   Orchestrator → Beta: 提供TargetInvariant + Alpha输出
   Beta → Orchestrator: 返回验证结果

3. 迭代优化阶段
   如果Beta有反驳/新增：
   Orchestrator → Alpha: 提供Beta反馈
   Alpha → Orchestrator: 返回修正后的列表
   重复步骤2-3直到收敛

4. 最终确认阶段
   当Beta全部同意或达到最大迭代次数
   输出最终Pre-Invariant列表
```

### 4.2 收敛策略
- **共识收敛**: Beta全部同意，无新增建议
- **稳定收敛**: 连续两轮没有实质性变化
- **强制收敛**: 达到最大迭代次数（建议3-5轮）
- **人工介入**: 存在无法调和的分歧时

### 4.3 分歧处理
当Alpha和Beta存在根本分歧时：
1. 记录双方观点和理由
2. 标记为"争议项"
3. 可选：引入第三方视角或人工裁决
4. 保留审计轨迹供后续分析

---

## 五、高级特性

### 5.1 层次化Pre-Invariant
识别Pre-Invariant之间的依赖关系：
- **基础层**: 最基本的存在性和定义性条件
- **关系层**: 实体间关系的约束条件  
- **全局层**: 系统级的一致性条件
- **领域层**: 特定应用领域的业务约束

### 5.2 条件化Pre-Invariant
某些Pre-Invariant可能是条件性的：
```
IF [特定场景] THEN [需要的Pre-Invariant]
```
这允许更精细的前置条件管理。

### 5.3 Pre-Invariant强度分析
- **强制性**: 绝对必要，否则Target Invariant无意义
- **保护性**: 防止边界情况，提高鲁棒性
- **优化性**: 简化验证，但非绝对必要

---

## 六、实践指南

### 6.1 启动建议
1. **从简单开始**: 先处理直观的Target Invariant
2. **积累经验**: 记录成功的模式，但保持开放思维
3. **领域适应**: 根据具体领域调整思考重点
4. **持续改进**: 基于实践反馈优化Agent行为

### 6.2 常见陷阱
1. **过度约束**: 添加"安全但不必要"的条件
2. **循环依赖**: Pre-Invariant之间形成循环
3. **层次混淆**: 混淆不同抽象层次的条件
4. **隐含假设**: 依赖未明确表达的假设

### 6.3 质量保证
1. **可追溯性**: 每个Pre-Invariant都有清晰的推理链
2. **可测试性**: 可以构造测试用例验证
3. **可理解性**: 非专家也能理解基本逻辑
4. **可维护性**: 随系统演化容易更新

## 七、扩展与集成

### 7.1 工具集成
- 支持导出为形式化验证工具的输入格式
- 提供API供其他系统调用
- 集成到CI/CD流程中

### 7.2 知识管理
- 构建Pre-Invariant模式库
- 支持跨项目的经验共享
- 但避免机械套用

### 7.3 人机协作
- 专家可以提供领域知识hints
- 支持交互式的探索和验证
- 保留人工override能力

---

## 八、评估标准

### 8.1 效果评估
- **完整性**: 是否找到所有必要的Pre-Invariant
- **精确性**: Pre-Invariant是否恰到好处
- **效率性**: 收敛速度和资源消耗
- **实用性**: 输出是否可直接应用

### 8.2 过程评估  
- **推理质量**: Alpha的发现逻辑是否清晰
- **验证质量**: Beta的审查是否全面
- **协作效率**: Alpha-Beta交互是否高效
- **知识积累**: 是否产生可复用的洞察

---

## 九、未来展望

### 9.1 智能化提升
- 自动学习常见的Pre-Invariant模式
- 基于历史数据优化发现策略
- 智能预测可能的遗漏点

### 9.2 规模化支持
- 并行处理多个Target Invariant
- 支持大规模系统的分析
- 分布式Agent协作

### 9.3 生态建设
- 开放的Pre-Invariant知识库
- 社区驱动的最佳实践
- 跨领域的经验交流

---

此框架设计追求在通用性和实用性之间的平衡，既不限制具体领域，又提供足够的方法论指导。核心理念是通过Alpha的创造性发现和Beta的批判性验证，形成高质量的Pre-Invariant挖掘能力。

## 十、智能化与自适应框架

为了进一步提升Deepener Agent的能力，引入以下智能化和自适应机制，使其从一个固定的工作流演变为一个能够根据问题动态调整策略的学习系统。

### 10.1 动态策略调整 (Dynamic Strategy Adaptation)
- **复杂度感知**: Alpha和Beta在开始时首先评估Target Invariant的复杂度（例如，涉及的变量数量、状态空间大小、逻辑深度）。
- **策略切换**:
    - **简单问题**: 采用“快速模式”，减少思考框架的检查点，追求效率。
    - **复杂问题**: 自动切换到“深度模式”，启用所有思考框架，并可能增加迭代轮数。
    - **不确定问题**: 采用“探索模式”，Alpha被鼓励提出更多样化的、甚至是看似不相关的Pre-Invariant，Beta则侧重于验证其相关性。

### 10.2 资源预算管理 (Resource Budget Management)
- **预算输入**: 在初始输入中增加 `max_tokens` 或 `max_iterations` 预算。
- **成本意识**: Alpha和Beta的每次调用都会消耗预算。Agent需要在预算内达成最佳结果。
- **最优决策**: 当预算紧张时，Agent会优先处理最关键的Pre-Invariant（可结合5.3节的强度分析），或者Beta会优先挑战最可疑的假设。

### 10.3 博弈论激励机制 (Game Theory Incentives)
- **奖励与惩罚**:
    - Alpha每提出一个被Beta“同意”的Pre-Invariant，获得正分。
    - Alpha每提出一个被Beta“反驳”的，被扣分。
    - Beta每成功“反驳”一个或“新增”一个被最终采纳的，获得正分。
- **收敛目标**: 整个系统的目标是最大化总分，这会激励Alpha提出高质量的假设，并激励Beta进行有建设性的挑战，从而更快地达成高质量共识。

### 10.4 结构化因果推断 (Structured Causal Inference)
- **因果链输出**: 要求Alpha在“发现理由”中，以结构化的方式（如 `A -> B -> C`）描述从Pre-Invariant到Target Invariant的因果路径。
- **Beta的因果验证**: Beta的任务不仅是验证Pre-Invariant，还要验证Alpha提出的因果链是否成立，并指出其中的逻辑跳跃或薄弱环节。

### 10.5 元认知与自我反思 (Metacognition and Self-Reflection)
- **迭代后反思**: 在每一轮迭代结束后，增加一个“反思”步骤。
    - **Alpha反思**: “我为什么会遗漏Beta新增的这个条件？我的哪个思考维度有盲点？”
    - **Beta反思**: “我的反驳是否过于苛刻？是否存在更简单的反例？我是否正确理解了Alpha的意图？”
- **学习与进化**: 反思的结果会作为上下文输入到下一轮，或用于长期优化Agent的行为模式。

### 10.6 假设空间探索 (Hypothesis Space Exploration)
- **多样性生成**: 鼓励Alpha使用不同的`temperature`参数生成多组候选Pre-Invariants，代表不同的“思想分支”。
- **并行验证**: Beta可以并行地验证这些不同的分支。
- **剪枝与合并**: Orchestrator根据Beta的反馈，剪掉不成立的分支，并尝试合并不同分支中的有效Pre-Invariants，形成更完整的集合。

这些补充将使Deepener Agent框架从一个静态的专家系统，演进为一个动态的、自适应的、具备学习能力的智能系统，能够更高效、更智能地应对各种复杂挑战。
